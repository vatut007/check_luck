# 001. Период акции и часовые пояса

## Контекст

Время на фискальном чеке (и в его QR-коде, `t=20261015T1830`) — это локальное
время кассы. Часового пояса в этом времени нет: чек из Владивостока и чек из
Калининграда выглядят одинаково, хотя реальная разница во времени — 7 часов.

Нужно решить, что значит «покупка в период акции», когда период задан просто
датами (`PROMO_START=2026-10-01`, `PROMO_END=2026-10-31`).

## Варианты

1. **Конвертировать по часовому поясу браузера** пользователя. Отбрасывается:
   пользователь может регистрировать чек с другого устройства или через
   прокси/VPN — часовой пояс браузера никак не связан с часовым поясом кассы,
   на которой выбили чек.
2. **Конвертировать по `PROMO_TIMEZONE`** (считать, что время на чеке — это
   московское время). Отбрасывается: для чека из Владивостока это физически
   неверно и может искусственно вытолкнуть покупку за пределы периода.
3. **Не конвертировать вообще.** Дата на чеке читается буквально, как её
   видит кассир, и сравнивается с `[PROMO_START, PROMO_END]` без пересчёта.

## Решение

Вариант 3. Условия акции формулируются для людей («покупки с 1 по 31
октября»), а не в UTC. `purchase_datetime` интерпретируется в `PROMO_TIMEZONE`
только для того, чтобы у Django было aware-значение (`USE_TZ=True`), — это не
настоящая конвертация, а технический тег. Проверка периода делает
`purchased_at.astimezone(PROMO_TZ).date()` и сравнивает с границами периода;
поскольку тег и искомая зона совпадают, конвертация оказывается тождественной
и просто возвращает ту же календарную дату, что была введена.

Проверка «чек не из будущего» сделана с допуском **14 часов** — это
максимальная разница поясов в РФ (Калининград UTC+2, Камчатка UTC+12) плюс
запас. Без допуска покупка в 01:00 по камчатскому времени 1 октября выглядела
бы как покупка «из будущего» по серверным часам (UTC+3).

См. `receipts/validators.py::validate_purchase_datetime`.

## Последствия

- Покупка 31 октября в 23:30 по Владивостоку (UTC+10) засчитывается, хотя по
  Москве это ещё 16:30 того же дня — и наоборот, никакого отдельного кода для
  этого не нужно, потому что дата просто не трогается.
- Часовой пояс браузера не используется вообще, даже как подсказка.
- Если возникнет требование по-настоящему учитывать пояс кассы (например, он
  станет приходить в QR), придётся переписать эту проверку — сейчас она
  сознательно упрощённая.
