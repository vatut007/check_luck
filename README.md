# Чек на удачу

[![CI](https://github.com/vatut007/check_luck/actions/workflows/ci.yml/badge.svg)](https://github.com/vatut007/check_luck/actions/workflows/ci.yml)

Промо-акция: пользователь регистрирует чек на сумму от 1000 ₽, модератор
принимает или отклоняет его, принятые чеки участвуют в розыгрыше призов.

## Быстрый старт

```bash
docker compose up
```

Поднимет Postgres и веб-контейнер, применит миграции и раздаст сервер на
http://localhost:8000/. Файл `.env` не обязателен — без него берутся
настройки из `.env.example`; создайте свой `.env`, только если хочется
поменять параметры акции.

После этого доступны:

| Адрес | Что это |
|---|---|
| http://localhost:8000/ | редирект в личный кабинет (анонима — на вход) |
| http://localhost:8000/accounts/signup/ | регистрация |
| http://localhost:8000/cabinet/ | личный кабинет (после логина) |
| http://localhost:8000/receipts/new/ | регистрация чека |
| http://localhost:8000/admin/ | админка модератора |
| http://localhost:8000/api/docs/ | Swagger |

Чтобы сразу получить демо-данные (тестовых пользователей, чеки, проведённый
розыгрыш), выполните ещё:

```bash
docker compose exec web python manage.py seed_demo
```

Логины (пароль = логину, кроме отдельно указанных):

- `demo` / `demo` — обычный пользователь, 25 чеков во всех статусах, включая выигрыш;
- `moderator` / `moderator` — staff + полные права, видит и модерирует все чеки;
- `stranger_demo` / `stranger_demo` — второй пользователь с парой чеков (чтобы убедиться, что чужие чеки не видны);
- `participant0` … `participant14` — участники общего розыгрыша.

На Linux/macOS то же самое можно сделать короче через `make`: `make demo`
(поднимает стек и сразу сидирует демо-данные), `make up`, `make down`,
`make test`, `make lint`, `make shell`, `make logs`.

### Почему сессия в cookie, а не токен в localStorage

Фронт и API живут на одном домене, поэтому не нужен отдельный механизм
авторизации для SPA. Сессия (`sessionid`) помечена `HttpOnly` — JS не может
её прочитать, значит XSS не может её украсть. CSRF-токен лежит в отдельной
читаемой cookie (`csrftoken`), которую `api.js` сам кладёт в заголовок
`X-CSRFToken` на небезопасных методах — стандартная связка Django +
`SessionAuthentication`, без JWT и без ручной инвалидации токенов.

## Обязательная часть

- [x] Вход и регистрация пользователя — `/accounts/login/` и `/accounts/signup/`
  (дефолтные формы Django, `UserCreationForm`).
- [x] Регистрация чека — форма `/receipts/new/` и `POST /api/receipts/`, с
  проверкой ФН/ФД/ФП/суммы/даты покупки по единым правилам с сервера
  (`GET /api/promo/`), с фото или без.
- [x] Личный кабинет участника — `/cabinet/` и `GET /api/receipts/`: список
  своих чеков с сортировкой, пагинацией, статусом и причиной отказа/текстом
  о выигрыше; изоляция чужих чеков — ни в API, ни в кабинете, ни в URL фото
  нет способа получить доступ к чужому чеку.
- [x] Модерация в админке — принять/отклонить (с обязательной причиной
  отказа), история переходов статуса.
- [x] Розыгрыш призов среди принятых чеков — проведение из админки,
  подробности и проверка воспроизводимости — в разделе
  [«Проверяемый розыгрыш»](#проверяемый-розыгрыш) ниже.

## Сверх задания

- Тесты: 190+ тестов (`pytest`), включая честный тред-тест на гонку при
  одновременной регистрации одного чека.
- Разбор QR-кода чека (бонусное поле на форме, свой API-эндпоинт).
- Фото чека: проверка по содержимому файла, снятие EXIF, миниатюра 104×104,
  приватная отдача (не из `/media/`).
- Live-обновление статусов в кабинете: polling с `ETag`/`If-None-Match`,
  пауза при скрытой вкладке.
- Выгрузка принятых чеков в CSV (с BOM, под Excel) прямо из админки.
- Проверяемый розыгрыш призов — см. ниже отдельный раздел.
- История статусов каждого чека (`ReceiptStatusLog`), видна в админке.
- Единый источник правил акции: период, минимальная сумма и длины реквизитов
  отдаются эндпоинтом и используются и серверной, и клиентской валидацией —
  поменялся `.env`, поменялось всё сразу.
- Сортировка кабинета и API по нескольким полям с белым списком.
- Приватная отдача фото чека с проверкой владельца (или staff).
- Идемпотентная команда `seed_demo` для быстрого ревью.
- CI на GitHub Actions (ruff + pytest на реальном Postgres).
- Swagger/OpenAPI-документация API (`drf-spectacular`).
- Прогрессивное улучшение формы регистрации: без JS она просто работает как
  обычный POST с серверным рендером ошибок, JS добавляет живую валидацию и
  экран успеха без перезагрузки.
- Доступность формы: `aria-invalid`/`aria-describedby` на полях с ошибкой,
  фокус переводится на первое невалидное поле.

## Проверяемый розыгрыш

Любой может повторить выбор победителей и убедиться, что он не подкручен
вручную.

1. В админке → «Розыгрыши» → «Добавить» указываете название приза и число
   победителей; зерно (seed) можно оставить пустым — сгенерируется само.
2. После проведения розыгрыш становится доступен только для чтения: зерно,
   хэш списка участников и сами победители со ссылками на их чеки видны на
   странице розыгрыша.
3. Проверка: `docker compose exec web python manage.py verify_draw <id>`.
   Команда пересчитывает хэш участников и повторяет выбор победителей тем же
   `seed` и тем же алгоритмом (`services.pick_winners`) — если всё совпало,
   выводит `OK`, иначе показывает, что именно разошлось, и завершается с
   ненулевым кодом.

Почему `random.Random(seed)`, а не `secrets`: нужна воспроизводимость по
известному зерну, а не криптографическая случайность каждого вызова.
Непредсказуемость обеспечивает само зерно — пока розыгрыш не проведён, оно
никому не известно (генерируется `secrets.token_hex`, если не задано
вручную). Подробности и альтернативы — в
[`docs/decisions/003-draw.md`](docs/decisions/003-draw.md).

## Что не успели или сознательно не делали

- Страницы «Правила» и «Профиль» в шапке — заглушки (`href="#"`), ссылка
  «На сайт» ведёт на условную домашнюю страницу, а не на реальный внешний
  сайт.
- Уведомления о выигрыше (email/push) — победитель узнаёт о выигрыше только
  при следующем визите в кабинет.
- Страница логина сделана минимальной и не по макету — в предоставленных
  экранах Figma её не было, это чисто техническая страница для локального
  входа.
- Google Sans из макета недоступен в Google Fonts — заменён на Manrope
  (ближайший шрифт с кириллицей).
- Мобильная раскладка таблицы кабинета сделана через подписи у ячеек
  (`data-label` + CSS), а не точным повторением группировки блоков из
  макета.
